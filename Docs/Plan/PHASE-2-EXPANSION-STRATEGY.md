## 1. 이 문서의 전제

이 문서는 **현재 프로젝트의 구조를 바꾸자는 문서가 아니다.**

현재 프로젝트의 기준은 그대로 유지한다.

- 현재 프로젝트는 `웹 패널 유지`
- 현재 MVP 구조는 `패널 -> 로컬 서버 -> Unreal 클라이언트`
- 지금 당장 `클라이언트가 패널까지 직접 호스팅하는 구조`로 갈아타는 것이 목적이 아님

이 문서의 목적은 아래 두 가지다.

1. 현재 구조가 다음 프로젝트의 베이스로 재사용 가능한지 판단
2. 다음 프로젝트에서 `Client App = 게임씬 + 패널 제공 주체 + 로컬 런타임` 구조로 확장 가능한지 검토

즉, 이 문서는 `현재 구조 폐기`가 아니라 `현재 구조의 확장 가능성 검토 문서`다.

## 2. 현재 프로젝트 구조 정의

현재 프로젝트의 실제 구조는 아래와 같다.

`모바일 웹 패널 -> ASP.NET Core 로컬 서버 -> Unreal 클라이언트`

세부 역할:

- `모바일 웹 패널`
사용자가 휴대폰에서 접속하는 제어 UI

- `로컬 서버`
명령 수신, SignalR/HTTP 처리, Unreal 전달, 향후 AI 오케스트레이션 확장 지점

- `Unreal 클라이언트`
게임씬 실행, 캐릭터/카메라/연출 반응 처리

보조 흐름:

- Unreal 실행 시 로컬 서버 자동 실행
- Unreal HUD에서 패널 접속용 URL 표시
- 패널은 같은 네트워크에서 브라우저로 접속

이 구조는 현재 MVP 목적에 맞다.

## 3. 현재 구조를 유지해야 하는 이유

현재 프로젝트에서는 웹 패널을 유지하는 것이 맞다.

이유는 다음과 같다.

1. 구현이 단순하다
패널과 Unreal 사이에 서버가 있으므로 책임이 분리된다.

2. 디버깅이 쉽다
패널, 서버, Unreal 로그를 분리해서 볼 수 있다.

3. 포트폴리오 설명력이 좋다
`입력 계층 -> 서버 런타임 -> 실시간 실행 계층` 구조를 설명할 수 있다.

4. AI 확장에 유리하다
AI API 호출, 상태 관리, 로그 축적은 서버 쪽에 두는 것이 가장 자연스럽다.

5. 다음 프로젝트로의 확장도 막지 않는다
현재 구조를 잘 정리해두면, 이후 `Client-centered` 구조로 가더라도 핵심 개념을 그대로 재사용할 수 있다.

## 4. 다음 프로젝트에 적용 가능한가

결론부터 말하면, **적용 가능하다.**

다만 "코드를 그대로 복붙"하는 수준이 아니라, 아래 개념을 재사용하는 식으로 보는 것이 맞다.

- 패널 입력 모델
- 명령 계약 모델
- 입력 / 해석 / 실행 분리 구조
- 실시간 전달 계층
- 캐릭터 반응 오케스트레이션 방식

즉, 다음 프로젝트에서 바뀔 수 있는 것은 `배치 방식`이고, 유지할 수 있는 것은 `아키텍처 개념`이다.

## 5. 다음 프로젝트에서 가능한 확장 방향

다음 프로젝트에서는 아래와 같은 형태가 가능하다.

### 방향 A. 현재와 유사한 구조 재사용

`웹 패널 -> 로컬 런타임 서버 -> 클라이언트`

이 방식은 가장 안전하다.

장점:

- 현재 프로젝트의 자산을 가장 많이 재사용 가능
- AI 기능 추가가 쉽다
- 멀티 패널 / 멀티 캐릭터 / 로그 저장으로 확장하기 좋다

### 방향 B. Client App 중심 구조로 확장

`패널 -> Client App -> 서버/AI API`

이 경우의 의미는 다음과 같다.

- Client App 하나가 게임씬도 실행하고
- 패널 접속용 웹앱도 제공하고
- 필요할 때만 서버 또는 AI API와 통신한다

여기서 중요한 점:

- 이것은 현재 프로젝트를 당장 이렇게 바꾸자는 의미가 아니다
- 다음 프로젝트에서 가능한 구조인지 검토하는 것이다

즉, 현재 프로젝트는 웹 패널 구조를 유지하되,
다음 프로젝트에서는 `Client App = Scene Host + Panel Host + Runtime Bridge`로 발전시킬 수 있다.

## 6. 현재 구조가 다음 프로젝트의 베이스가 될 수 있는 이유

현재 코드베이스에는 다음 프로젝트에도 유효한 핵심 베이스가 이미 있다.

### 6.1 명령 계약 분리

`Shared/Exhibition.Shared/Commands/ExhibitionCommand.cs`

이 구조는 매우 중요하다.

- `CharacterId`
- `TargetId`
- `SetEmotion`
- `PlayAnimation`
- `TriggerStageEvent`
- `MoveDirection`
- `Rotate`

이 명령 기반 설계는 다음 프로젝트에서도 그대로 응용 가능하다.

### 6.2 패널 입력과 전송 계층 분리

모바일 패널은 이미 `TransportProvider`, `SignalRTransport`, `HttpTransport`로 나뉘어 있다.

의미:

- 현재는 서버를 향해 전송하지만
- 다음 프로젝트에서는 `Client App` 내부 런타임이나 다른 전송 계층으로 교체 가능하다

즉, 웹 패널 자체는 다음 프로젝트에서도 계속 살아남을 수 있다.

### 6.3 Unreal 실행 계층 분리

Unreal 쪽도 다음과 같이 나뉘어 있다.

- 실시간 수신
- 명령 파싱
- 이동 입력 브리지
- HUD
- 스폰 매니저

이 분리 구조는 다음 프로젝트에서 입력 소스가 바뀌어도 재사용 가치가 높다.

### 6.4 서버가 AI 확장 포인트가 될 수 있음

현재 서버는 아직 얇지만, 다음 프로젝트에서는 이 서버 개념을 아래처럼 확장할 수 있다.

- 로컬 런타임 서버
- AI orchestration 서버
- 세션/상태 서버
- 원격 운영 서버

즉, 지금의 서버는 버릴 구조가 아니라 성장 가능한 구조다.

## 7. 다음 프로젝트에서 `Client App + Panel` 구조가 가능한가

가능하다.

다만 표현을 정확히 해야 한다.

다음 프로젝트에서 가능한 것은 아래 구조다.

`Client App`
- 게임씬 실행
- 웹 패널 파일 제공
- 패널 입력 수신
- 로컬 상태 관리
- 필요 시 외부 서버/AI API 호출

`Mobile Panel`
- 같은 네트워크에서 Client App이 제공하는 웹앱에 접속
- 명령을 Client App 쪽으로 전송

`Server / AI API`
- AI 응답 생성
- 로그 저장
- 세션/원격 관리

이 구조는 충분히 현실적이다.

하지만 이 구조에서도 본질은 동일하다.

- 입력 계층
- 해석/오케스트레이션 계층
- 실행 계층

즉, 배포 위치만 달라질 뿐 설계 철학은 같다.

## 8. AI 챗봇 연동 가능성

## 8.1 결론

`가능하다.`

그리고 현재 웹 패널 유지 구조에서도 충분히 가능하다.

즉, AI 챗봇을 위해 웹 패널 구조를 버릴 필요는 없다.

## 8.2 현재 프로젝트 기준 가능한 흐름

현재 구조에서 가장 자연스러운 흐름은 아래와 같다.

`패널 채팅 입력 -> 로컬 서버 -> AI API -> 로컬 서버 -> Unreal 클라이언트`

서버가 수행할 일:

1. 패널에서 텍스트 입력 수신
2. AI API로 질의
3. 응답을 `emotion + answer + optional action` 형태로 구조화
4. Unreal에 전달

Unreal이 수행할 일:

1. 감정 반응
2. 애니메이션 반응
3. 자막/대사 UI 표시
4. 필요 시 StageEvent 반응

즉, 현재 구조 자체가 이미 AI 응답을 얹기 좋은 형태다.

## 8.3 왜 서버를 거치는 것이 맞는가

AI 호출을 패널에서 직접 처리하는 것보다 서버를 거치는 편이 좋다.

이유:

1. API 키 보호
2. 프롬프트/응답 정책 중앙 관리
3. 감정 분류, 필터링, fallback 로직 관리 가능
4. 대화 로그 저장 가능
5. Unreal로 보낼 결과를 표준 명령으로 변환 가능

즉, AI는 `패널 직결`보다 `서버 오케스트레이션`이 맞다.

## 9. 다음 프로젝트를 위해 지금 구조에서 보강할 것

다음 프로젝트 적용 가능성을 높이려면 지금 구조에서 아래를 보강하는 것이 좋다.

### 9.1 서버를 Unreal 전용 브로드캐스터에서 공용 런타임으로 승격

현재는 `IUnrealBroadcaster` 중심이다.

다음 프로젝트까지 고려하면 아래 같은 중립 인터페이스가 더 낫다.

- `ICommandSink`
- `IRuntimeClient`
- `ICommandRouter`

이렇게 하면 다음 프로젝트에서

- Unreal
- Unity
- Native client
- 로컬 런타임 브리지

같은 다양한 수신 주체로 확장하기 쉬워진다.

### 9.2 라우팅 개념 추가

다음 프로젝트까지 고려하면 아래 값들이 필요하다.

- `SessionId`
- `ClientRole`
- `ProjectId`
- `TargetId`

현재는 브로드캐스트 중심이지만, 이후에는 대상 선택이 가능해야 한다.

### 9.3 명령 계약 확장

AI 기능까지 고려하면 아래 명령 타입이 필요할 수 있다.

- `ShowDialogueCommand`
- `CharacterResponseCommand`
- `ReportCharacterStateCommand`

처음부터 다 넣을 필요는 없지만, 다음 프로젝트까지 본다면 방향은 이쪽이 맞다.

### 9.4 패널 레거시 코드 정리

다음 프로젝트에 재사용하려면 모바일 패널에서 구형 `socket.io` 계열 파일은 정리하는 편이 좋다.

현재는 전송 구조가 이원화되어 있어 재사용 베이스로 보기엔 다소 혼재되어 있다.

## 10. 권장 로드맵

### Step 1. 현재 프로젝트 MVP 마감

- 웹 패널 유지
- QR 코드 추가
- 감정/연출 Blueprint 반응 검증
- 데모 흐름 정리

### Step 2. 서버 구조 정리

- 브로드캐스트 중심 구조 완화
- 라우팅 개념 추가
- 상태 관리/로그 확장

### Step 3. AI 채팅 MVP 추가

- 패널 텍스트 입력 추가
- 서버 AI 연동
- `emotion + answer` 응답 구조 도입
- Unreal 자막/반응 연동

### Step 4. 다음 프로젝트용 구조 일반화

- Client App이 패널까지 제공하는 배치 구조 검토
- 서버는 선택적 백엔드 또는 AI 오케스트레이터로 분리
- 현재 웹 패널과 명령 계약 재사용

## 11. 최종 결론

이 문서의 핵심 결론은 명확하다.

1. 현재 프로젝트는 웹 패널 구조를 유지하는 것이 맞다
2. 현재 구조는 다음 프로젝트에 적용 가능한 베이스가 된다
3. 다음 프로젝트에서는 `Client App + Panel + optional server` 구조로 확장 가능하다
4. AI 챗봇 연동은 현재 구조에서도 충분히 가능하며, 오히려 서버를 유지하는 편이 더 자연스럽다

즉, 현재 구조는 임시 구조가 아니라
`다음 프로젝트까지 이어질 수 있는 1차 아키텍처 베이스`
로 볼 수 있다.

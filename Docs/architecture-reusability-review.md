# 구조 재사용성 검토 메모

작성일: 2026-04-20

## 현재 판단
현재 구조는 `웹패널 -> 서버 -> UE 클라이언트` 형태의 1개 전시 MVP를 빠르게 만드는 데는 적합하다.  
하지만 추후 다른 프로젝트에서도 재사용할 수 있는 공용 베이스 구조로 보기에는 아직 부족하다.

핵심 이유:
- 서버 애플리케이션 계층이 `IUnrealBroadcaster`에 직접 의존하고 있어 Unreal 전용 흐름으로 고정됨
- 서버 라우팅이 없어 UE 연결 전체에 브로드캐스트하는 구조임
- 명령 스키마가 서버, 모바일, UE에 중복 정의되어 드리프트 위험이 큼
- 모바일 패널에 구형 `StageCommand` / `socket.io` 계열 코드가 남아 있어 기준 모델이 혼재됨

## 좋은 점
- 모바일 패널의 `TransportProvider`, `SignalRTransport`, `HttpTransport` 분리는 재사용 가치가 있음
- `Shared/Exhibition.Shared`에 공용 DTO 프로젝트가 이미 있음
- UE 입력 브리지가 컴포넌트로 분리되어 있어 캐릭터 측 재사용성은 비교적 좋음

## 우선 리팩토링 필요 항목
### 1. 서버 추상화 상향
`IUnrealBroadcaster` 중심 구조를 `ICommandSink`, `IRuntimeClient`, `ICommandRouter` 같은 중립적인 인터페이스로 바꾸는 것이 우선이다.

### 2. 라우팅 계층 추가
`Session`, `ClientRole`, `TargetId`, `ProjectId` 같은 기준으로 명령 대상을 선택할 수 있어야 한다.  
현재처럼 전체 브로드캐스트만 있는 구조는 다른 프로젝트 재사용에 불리하다.

### 3. 명령 스키마 단일화
서버가 기준 계약이 되고, 모바일과 UE는 그 계약을 따르게 정리해야 한다.  
UE 쪽 비어 있는 parser/DTO 파일은 실제 구현으로 채우는 방향이 맞다.

### 4. 레거시 코드 분리
`Mobile-Panel/src/types.ts`, `src/components/MobilePanel.tsx` 등 구형 모델은 제거하거나 `legacy/`로 격리하는 것이 좋다.

## 결론
전면 재작성까지는 필요 없어 보인다.  
다만 “다른 프로젝트에서도 쓸 수 있는 구조”를 목표로 한다면, 지금 단계에서 서버 중심 리팩토링은 한 번 해두는 것이 맞다.

## 다음에 이어서 볼 것

- 명령 계약을 어디까지 공통화할지
- UE 패널, 웹 패널, 다른 클라이언트 조합까지 감안한 라우팅 설계
